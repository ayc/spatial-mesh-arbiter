# SK-78: Fear

## Designer Intent

I terrify all nearby enemies for 2 seconds. Feared enemies run away from me uncontrollably — they cannot choose their direction, they just flee. They can't attack, cast, or control their movement during fear.

## Primitive Composition

P-03 (Trajectory Steering) → P-26 (Capability Bitmask)

*See `ability-primitives/` for canonical definitions.*

## Inputs

- Caster entity (the fear source)
- No target required (AoE centered on caster)

## Observable Behavior

1. Cast — all enemies within radius are feared for 2 seconds
2. Feared enemies automatically run directly away from the caster's position
3. Feared enemies cannot move voluntarily, attack, or cast (full disable + forced movement)
4. In this reference, the flee steering is recalculated relative to the caster's current position
   each tick
5. If a feared enemy hits a wall, they stop moving but remain feared (can't act)
6. Duration reduced by Tenacity
7. Subject to Diminishing Returns (SK-28) — hard CC category
8. Cleansable by SK-15 Purify
9. Visual: purple terror effect, enemy runs with panic animation

## Engine Primitives Required

Fear is already one of the canonical `apply_cc` behavior profiles.

The recommended lowering is:

1. apply one AoE `apply_cc` with:
   - `cc_type = fear`
   - `category = forced_movement`
   - `duration_ticks = 120`
   - `duration_scaling = status_resistance`
   - an authored `dr_category` if the game wants fear to participate in the same DR bucket as other
     forced-movement CC
2. let the generated fear status use the canonical profile:
   - suppress attacks and casts
   - emit deterministic steering away from the source each tick
   - remain cleansable like other ordinary negative CC unless the designer says otherwise

This keeps the mechanic entirely inside the canonical CC surface:

- fear is not a bespoke movement script
- the source-relative flee steering is generated by the `cc_type = fear` profile
- Tenacity / status resistance and DR are ordinary authored CC metadata

## Cross-Boundary Concerns

Fear follows the canonical target-owner forced-movement contract.

1. If the AoE admits a remote/Ghost target, the generated fear status is installed on the target's
   current owner through the ordinary CC relay path.
2. While fear is active, the target owner emits the per-tick steering locally using the current
   local-or-Ghost pose of the fear source.
3. If either endpoint hands off, the status transfers as ordinary SoftState and the new owner keeps
   reading the source through the same local-or-Ghost source-identity rule used by other source-tied
   CC profiles.

## Compiler Requirements

Designer specifies:

- AoE radius
- duration
- whether fear is cleansable
- whether fear participates in an authored DR bucket

Compiler emits:

- one AoE CC application with `cc_type = fear`
- the generated negative fear status carrying canonical source-relative steering semantics

Compiler validates:

1. `cc_type = fear` pairs only with `category = forced_movement`
2. the duration uses ordinary CC duration scaling / DR rules rather than a bespoke fear timer
3. the forced flee behavior is expressed through the canonical fear profile, not a custom per-tick
   movement script

## Resolved Interaction Notes

- Unstoppable and other ordinary CC-immunity effects block fear admission because fear is canonical
  CC in the `forced_movement` category.
- Fear does not break on damage in this reference. The profile-defined damage break belongs to
  sleep, not fear.
- Terrain walls and other blocking geometry still stop the movement because the steering feeds the
  ordinary movement/collision path; fear does not tunnel through walls.
- The source-relative flee vector is dynamic in this reference because that is the canonical fear
  profile currently documented by the compiler layer.
- If another ordinary displacement effect lands during fear, both effects resolve through the normal
  movement / displacement ordering rules; fear does not get a bespoke precedence override.
